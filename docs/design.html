设计说明

状态与合并规则

图的状态里有两个字段是并发写的：drafts（每个文件的审查结果）和 verdicts（校验结论）。 它们不用列表累积，而是用「按文件路径覆盖」的合并规则：

def merge_by_file(left, right):
    merged = dict(left or {})
    merged.update(right or {})
    return merged

一条规则同时解决三件事：

  • 多个文件的审查并发执行，各自写自己的键，互不覆盖；
  • 重做某个文件时，用同一个键写回去，旧结果被替换；
  • 人工打回时整批重做，键不变，结果整体刷新。

换成列表加 operator.add 就会出问题：重做一次，同一份意见会在列表里出现两次。

意见的 id

每条意见在进入状态时生成一个 8 位 id。校验结论、重做输入、报告条目都按这个 id 关联， 所以重做之后新旧意见不会串。

「有依据」拆成两层

要求模型「给出有依据的意见」本身没法判定。所以把它拆成两层：

位置层，纯代码判定。 在 verification.py 里比对：

  1. file_path 在本次改动里；
  2. line_start 到 line_end 内至少有一行属于新增行；
  3. evidence 的每一行去掉空白差异后，能在这次改动原文里找到；
  4. evidence 至少有一行落在所引用的行号区间内的新增行上。

这四条不需要模型，结果唯一，可以单独写测试。为了让第 3、4 条有得比，喂给模型的改动文本 带真实行号，提示词里明确要求逐字引用。

语义层，模型判定。 位置过关的意见才送去判断「这段代码能不能支持这个结论」。 不通过的位置层不会消耗模型调用。

这样「没依据就重新生成」有明确触发条件，不会变成模型自己跟自己争论。

重做与上限

verify 之后按条件分流：

有意见没通过 且 revision_round < max_rounds → revise
否则                                       → aggregate

revise 只重做没通过的那些意见，并把失败原因一并交给模型；通过的意见原样保留。 轮次上限默认 3，防止模型反复给不出可定位的引用时死循环。到了上限，没通过的意见 单独列进报告的「未通过校验」一节，交给人判断。

人工打回走同一个节点，区别是提示词里带上人工反馈，并且整批重做。打回时把 revision_round 归零，让它重新获得完整的重做轮次。

并行

两处并行：

  • classify 用 Send API 按文件扇出到 review_file，LangGraph 负责并发调度和汇合， 图级别由 max_concurrency 限流；
  • verify 和 revise 是单节点，但内部按文件用线程池并发，同样受 max_concurrency 限制。

人工确认与检查点

human_gate 用 interrupt() 原地暂停，节点的剩余部分在恢复时重新执行，所以 interrupt() 之前不能有副作用。

检查点先内存后 SQLite。内存检查点只在进程内有效；换 SQLite 之后状态落盘， 进程退出后可以用会话 id 在另一个进程里接着跑（review resume --thread <id>）。

状态里不放 API 密钥：Settings.for_state() 会把它去掉，密钥由各节点在需要时从环境变量读。 这样检查点文件和日志里都不会出现密钥。

自定义类型进检查点需要在序列化器里显式放行，见 graph.py 的 make_serde()。
